## Что за продукт

Локальное (офлайн) настольное приложение для **проверки и правки корпоративных документов**: договоры, приказы, служебные записки, регламенты, ТЗ. Пользователи — бухгалтеры, юристы, канцелярия.

Главный сценарий: загрузить документ (DOCX/PDF/скан) → система находит ошибки и несостыковки → правки показываются «как в Git» (было/стало + комментарий «что не так»), принимаются по одной или все сразу → сохраняются версией → экспорт обратно в DOCX/PDF. Плюс поиск по базе и ИИ-ассистент со сводками («утверждённые бюджеты» → «за декабрь» → таблица сумм с источниками).

Документы ТЗ (Claude Docs, читать через инструменты docs по ссылке):
- ТЗ: https://claude.ai/artifact/AAroyuVv3MejrJfhs8DbsM
- Каталог экранов и функций: https://claude.ai/artifact/1zXfF8Ai3YRqHFoTW8j1du

### Железо
- **Целевые ПК покупателей**: офисные, 8–16 ГБ ОЗУ, видеокарта 1–2 ГБ (бесполезна для LLM) → всё ИИ на процессоре. Бюджет памяти приложения: ≤3,5 ГБ (8 ГБ ПК), ≤6 ГБ (16 ГБ ПК). Модели: 1,5B (лёгкий профиль) / 3–4B (стандарт) в Q4 через llama.cpp.
- **ПК пользователя (разработка, демо, дообучение)**: RTX 5070 12 ГБ, Ryzen 7 7800X3D, 32 ГБ DDR5. Подходит для QLoRA 7–8B и LoRA 3–4B; Blackwell требует свежих CUDA/PyTorch.

## Архитектура

```
Documentum.exe (C# лаунчер, DocumentumLauncher.cs) — запускает и сторожит службы
 ├─ Интерфейс: Electron, document-intelligence/electron-app/src/renderer/v2 (старый UI: флаг --legacy)
 │    сборка для лаунчера: portable-ui/Documentum-UI.exe (npm run build:portable)
 ├─ Сервер данных: Java 21 / Spring Boot, document-intelligence/java-backend, порт 8085, БД H2 (ddl-auto: update)
 └─ AI-сервис: Python / FastAPI, document-intelligence/ai-service, порт 8000 (запускается из исходников через venv)
```

Ключевые места кода:
- **UI v2**: `index.html`, `styles.css`, `screens.css`, `app.js` (редактор, правки, ассистент, версии демо), `real.js` (клиент API, настоящие документы, пометки проверок, сравнение версий, экспорт), `screens.js` (обзор, реестр, поиск, настройки, импорт/экспорт), `demo-data.js` / `demo-docs.js` (демо-договор 124-А, бюджеты, 23 демо-документа). Порядок скриптов: demo-data → demo-docs → app → real → screens.
- **Java**: `controller/EditorController.java` (`/api/editor/documents/...`), `service/EditorService.java` (импорт, версии, черновик, проверка, индексация, поиск), `entity/Document.java`, `entity/DocumentVersion.java`, `service/AiServiceClient.java`.
- **Python**: `app/editor/converter.py` (DOCX/PDF/скан/TXT → HTML), `app/editor/exporter.py` (HTML → DOCX), `app/checks/` (правила проверки), `app/search/` (стеммер, поля карточки, индекс BM25 в `ai-service/data/search.db`), эндпоинты в `app/main.py` (`/editor/*`, `/search/*`).

Важный инвариант: **нумерация абзацев** на сервере (`app/checks/blocks.py`) и в редакторе (`pageBlocks()` в `real.js`) одинакова — блоки `h1,h2,h3,p,li,td,th`, не вложенные друг в друга. Находки проверки и результаты поиска ссылаются на «блок + смещение»; при расхождении текста UI ищет цитату.

`cleanHTML()` в `real.js` снимает служебные пометки (`.sug`, `.note`, `[data-rid]`, `mark.search-hit`) — всё, что сохраняется на сервер, проходит через неё.

### Проверки этапов 6–7 — как устроены
- `POST /editor/check` принимает `docId` и `deep`; Java: `POST /api/editor/documents/{id}/check` с `{html, deep}`, в ответе на свежую проверку есть `semantic` и `cross` (сведения о проходе). У находки появились поля `ai` и `source` (`{text, doc, docId, block, start, end}`); интерфейс показывает пометку «ИИ» и ссылку «Открыть» на документ-источник.
- **Типовые риски** — правило `risks` в `checks/rules.py`, без модели: неустойка ≥ 0,5 % в день, неустойка за каждый день без предела, автопродление, односторонний порядок, невозврат аванса, срок без числа. Категория «Риски».
- **Сверка с базой** — `checks/cross.py`, работает при каждой проверке: тексты других документов берутся из поискового индекса (`index.docs`, профиль документа кэшируется в записи индекса). Сверяет ИНН/КПП/счёт организации с другими документами (замечание, только если большинство документов говорит другое), один ИНН у разных названий, подписанта («в лице …»), ссылки «по договору № … от …» — дату, стороны, сумму счёта/акта против цены договора. Копии проверяемого документа не учитываются. Если ссылки на документ в базе нет — молчит.
- **Смысловая проверка моделью** — `checks/semantic.py`, только по кнопке (`deep`): текст кусками по 3000 знаков, не больше 4 кусков; модель отвечает строками `ТИП | номер фрагмента | цитата | пояснение`. Находка принимается, только если цитата найдена в тексте; «противоречие» — только между двумя разными абзацами с числами. На договоре в 4 тыс. знаков — около минуты. **Qwen3-4B судит слабо**: на настоящем договоре дала надуманные находки и пропустила пени 10 % в день (их теперь ловит правило). Польза от этой проверки пока небольшая — кандидат на более сильную модель или дообучение.
- Две находки на одном месте: пометка остаётся одна (более важная), пояснение и `source` второй дописываются к ней (`engine.py`).
- Тесты: `tests/test_cross.py` (сверка, смысловая проверка с подставной моделью, риски).
- **Орфография по словарю** — `checks/speller.py` + правило `dictionary_spelling`. Словарь hunspell из LibreOffice лежит в репозитории: `app/checks/dict/ru_RU.dic`, `.aff` (139 тыс. слов, BSD, автор А. И. Лебедев — `README_ru_RU.txt` обязан идти вместе). Библиотека hunspell не нужна: разобраны только правила окончаний (SFX). Замечание ставится, только если слова нет в словаре **и** в одной правке от него есть известное слово; проверяются лишь слова из строчных русских букв от 5 знаков; пропускаются формы, отличающиеся от замены одним окончанием, и слова, чья основа встречается в документе 2+ раза (термины). На трёх настоящих документах — одно ложное срабатывание («ревью»). `pyspellchecker` не подошёл (20 тыс. слов без падежей) и удалён.

### Поставка (этап 8)
- `packaging/build-dist.ps1` собирает `dist/Documentum` (в `.gitignore`): лаунчер (компилируется `csc` из `DocumentumLauncher.cs`), `runtime/python` (базовый Python + `site-packages` из venv), `runtime/jre` (jlink из JDK 21), `runtime/paddlex` (модели распознавания сканов из `~/.paddlex`), интерфейс, jar, AI-сервис, по одной языковой модели и модели отпечатков. Ключ `-NoModels` — без моделей. Файлы `.ps1` и `.iss` — в UTF-8 с BOM, иначе PowerShell 5.1 портит русские буквы.
- Лаунчер сначала ищет `runtime\python\pythonw.exe` и `runtime\jre\bin\javaw.exe` рядом с собой, потом — как раньше (venv, системные). `run.py` при наличии `runtime\paddlex` выставляет `PADDLE_PDX_CACHE_HOME`. **`Documentum.exe` в корне репозитория не пересобирался** — он старый, в нём этих строк нет; для разработки это не важно.
- `packaging/Documentum.iss` — сценарий Inno Setup: установка в профиль пользователя без прав администратора (база лежит в папке программы), деление на части по 2 ГБ. Собирается: `& "C:\Program Files\Inno Setup 7\ISCC.exe" /Q packaging\Documentum.iss` (4–5 минут) → `dist\Documentum-Setup.exe` + `Documentum-Setup-N.bin`; все файлы передаются вместе. **Сам установщик не запускался** — установка на чистый ПК не проверена.
- `document-intelligence/docs/Инструкция.md` — инструкция пользователя, кладётся в поставку.
- **Замер на компьютере покупателя**: `packaging/measure.ps1` (+ `measure.cmd`) кладутся в поставку как `measure.ps1` и `Замер.cmd`. Скрипт при запущенной программе берёт самый большой документ базы, засекает проверку, два вопроса по документу (первый — с загрузкой модели), вопрос по базе, поиск по смыслу и смысловую проверку, снимает память трёх частей программы и пишет `замер.txt` рядом с собой (`-Quiet` — не открывать Блокнот). `packaging/run-light.cmd` → `Запуск в лёгком профиле.cmd`: запуск с `DOCUMENTUM_PROFILE=light`. Тексты `.cmd` — латиницей (cmd читает файл в кодировке консоли). Проверено на ПК пользователя: первый вопрос 26 с, второй 10 с, смысловая проверка короткого договора 12 с, память 5,4 ГБ.
- Пользователь собирается прогнать замер на ноутбуке Ryzen 5 5500U / 16 ГБ DDR4 в обоих профилях — ждём два файла `замер.txt`.
- В поставку идут три модели: основная (`models/`), лёгкая (`models/light/`) и отпечатков (`models/embed/`); скрипт берёт из каждой папки первый файл по побуквенному порядку имён, как и программа.
- Проверено: поставка 5,6 ГБ с лёгкой моделью (без неё 4,5 ГБ: Python 979 МБ, модели ~3 ГБ, интерфейс 285 МБ, Java 61 МБ, OCR 136 МБ), собирается за 40 с; вложенный Python импортирует сервис и находит модели, вложенная Java поднимает jar на тестовом порту. **Не проверено**: запуск всей поставки её собственным лаунчером и работа на чистом ПК без Java/Python.
- **Замер памяти на ПК пользователя** (обе модели и OCR загружены, после вопроса ассистенту): AI-сервис 4,9 ГБ, сервер данных 0,46 ГБ, интерфейс 0,3 ГБ — всего 5,7 ГБ. В бюджет 6 ГБ для ПК с 16 ГБ укладывается впритык, для ПК с 8 ГБ (3,5 ГБ) — нет: там нужны лёгкая модель и отключение смыслового поиска.

### Ассистент (этап 6) — как устроен
- `ai-service/app/assistant/engine.py`: разбор вопроса (тип, период, контрагент, сроки, замечания, группировка, остаток слов → поиск по тексту), отбор по карточкам, суммы, источники «блок + смещение». Цифры и список считаются точно; модель только формулирует вывод по готовым фактам (ссылки на несуществующие источники вырезаются).
- `ai-service/app/assistant/llm.py`: необязательная модель через `llama-cpp-python` 0.3.36 (стоит в venv); файл `.gguf` кладётся в `ai-service/models/` (папка в `.gitignore`; или путь в `DOCUMENTUM_LLM_MODEL`, размер контекста — `DOCUMENTUM_LLM_CTX`, по умолчанию 4096). Нет библиотеки или файла — ассистент работает по шаблону. Загружается при первом вопросе, `use_mmap=False` (с mmap на Windows процесс занимал 4,7 ГБ вместо 3,1 ГБ).
- **Замер Qwen3-4B Q4_K_M** (`Qwen/Qwen3-4B-GGUF`, 2,5 ГБ) на ПК пользователя, только процессор: загрузка 2 с, ~15 токенов/с, ответ ассистента 5–10 с, память процесса 3,1 ГБ. Потоков больше 4 скорость не прибавляют. Это профиль «Стандарт» (16 ГБ); для 8 ГБ ПК — лёгкая модель QVikhr-1.7B (см. ниже).
- **Qwen3.5-4B Q4_K_M** (`unsloth/Qwen3.5-4B-GGUF`, 2,7 ГБ) тоже скачана и запускается: отвечает подробнее, но медленнее (7–12 с) и один раз связала факты выдуманным условием. Основная — Qwen3-4B: без переменной окружения берётся первый по алфавиту файл `.gguf`, это она.
- В модель уходят строки «[n] название; дата; контрагент; сумма; цитаты» (до двух лучших сниппетов поиска — у сниппета есть `rank`, 0 = самый подходящий). Если у документа нет суммы, это пишется явно — иначе модель приписывает ему общий итог.
- Эндпоинты: Python `/assistant/ask`, `/assistant/status`; Java `POST /api/editor/documents/assistant` (сам собирает карточки из базы), `GET .../assistant/status`. Уточнения («за ноябрь», «по контрагентам») работают через `context` из прошлого ответа — клиент присылает его обратно.
- **Вопрос по одному документу** («Спросить ИИ» в редакторе): `ask_document()` в `engine.py`, в запросе `docId`. Документ до 5000 знаков уходит в модель целиком, длиннее — 8 лучших абзацев + заголовки разделов; если к вопросу подошёл заголовок раздела, в модель уходит и текст раздела (`_with_sections()`, до 1500 знаков на раздел, всего до 3600 — иначе ответ дольше 20 с). Все заголовки разделов добавляются отдельными нумерованными фрагментами (`_with_outline()`) — модель видит строение документа и может сослаться на каждый раздел; `_fix_heading_refs()` чинит ссылки рядом с названиями разделов (номер раздела вместо номера фрагмента, одна общая ссылка на перечень), `_clean_refs()` разворачивает «[7–11]». Модель просят пересказать содержание в 2–5 предложениях со ссылками; оборванный по длине ответ обрезается до целого предложения. Ответ на длинном документе — 14–20 с. Ответ: `kind: "doc"`, `sources` (блок + смещение). UI — `askRealDoc()` в `app.js` (для демо-договора остались демо-ответы). Текст берётся из индекса, то есть из последней сохранённой версии, а не из несохранённого черновика.
- **Вопрос по содержанию** в общем ассистенте (нашлось по тексту, без типа/контрагента/периода и без слов про деньги): суммы из карточек не показываются и не складываются (`by_text`). «Сколько» означает деньги, только если других слов в вопросе не осталось. Одинаковые документы (копии) уходят в модель один раз, пользователю — предупреждение.
- `_tidy()` убирает дежурное «в документе это не указано» после содержательного ответа и ссылки у ответа «не указано».
- Сумма в карточке (`search/fields.py`): «число (скобки)» — сумма, только если в скобках число прописью и рядом рубли. При смене правил разбора поднять `SearchIndex.VERSION` — индекс очистится, сервер данных при старте пришлёт документы заново и пересчитает карточки.
- **Смысловой индекс по абзацам** (`search/embed.py`, `search/index.py`): модель отпечатков — `.gguf` в `ai-service/models/embed/` (или `DOCUMENTUM_EMBED_MODEL`), сейчас Qwen3-Embedding-0.6B Q8 (640 МБ, Apache 2.0). Вектор обрезается до 256 чисел, хранится в таблице `chunks` по контрольной сумме текста абзаца: при сохранении пересчитываются только изменённые абзацы, копии документов не считаются вовсе. Расчёт — в фоновом потоке (`embed_pending()`; в тестах `background=False`). Режим поиска `sem` добавляет документы с близостью ≥ `SIM_MIN` (0,5; у посторонних запросов 0,37–0,48); ассистент учитывает близость при выборе абзацев (`_fragments(..., sims)`). Нет модели — всё работает по словам и синонимам.
- Замер на ПК пользователя: 0,16–0,4 с на абзац, запрос 0,13 с, память +0,95 ГБ (n_ctx/n_batch 512; при 1024 было 1,5 ГБ). 5 документов (576 абзацев, из них 216 разных) — 40 с; правка одного абзаца — 0,2 с. Вместе с языковой моделью это ~4 ГБ — только профиль «Стандарт» (16 ГБ). Маленькие модели не подошли: granite-107m находит верный абзац в 1 случае из 10 (Qwen — 9 из 10), GGUF-сборки e5-small сломаны (нет `token_type_count` либо не тот токенизатор).
- Состояние обеих моделей — `GET /assistant/status` (`search`: готово/всего абзацев), показывается в настройках.
- UI: `realPlan()` и `renderRealAnswer()` в конце `real.js`; `ask()` в `app.js` сначала спрашивает настоящую базу, демо-сценарии — если там ответа нет и демо-данные включены (`chat.mode`).
- Боковые панели редактора раздвигаются мышью (`panelResizers()` в `app.js`, переменные `--left-w` / `--right-w`, ширина хранится в localStorage, двойной щелчок по границе — сброс).
- Тесты: `tests/test_assistant.py` (добавить в список раннера).
- **Профили по памяти** (`llm.profile()`): меньше 12 ГБ ОЗУ — «light»: модель берётся из `models/light/`, модель отпечатков не загружается (поиск по словам); иначе «standard». Принудительно — `DOCUMENTUM_PROFILE=light|standard`. Профиль и объём памяти видны в настройках.
- **Лёгкая модель — QVikhr-3-1.7B-Instruction-noreasoning Q4_K_M** (`Vikhrmodels/...-GGUF`, 1,1 ГБ, Apache 2.0, дообучена на русском), лежит в `models/light/`. Замер на ПК пользователя: сводки ассистента 2–6 с (у Qwen3-4B 5–10 с), память 1,65 ГБ (против 3,1 ГБ), фактических ошибок на тестовых вопросах нет. На длинном документе теряется и перечисляет всё подряд, поэтому в лёгком профиле вопрос по документу получает 4 места вместо 8, до 2200 знаков и без оглавления (`_light_model()` в `engine.py`) — ответы по делу за 7–11 с, но вопрос «какие разделы в документе» без оглавления отвечается плохо. Кандидат на замену основной: `Vikhrmodels/QVikhr-3-4B-Instruction-GGUF` (2,5 ГБ, тоже русская) — не скачивалась и не сравнивалась.
- Осталось по этапу 6: замер на настоящем слабом ПК. Состояние модели в настройках (раздел «Искусственный интеллект») уже настоящее; остальное на этой странице — макет.

Открытые хвосты: TXT с одиночными переводами строк склеивает строки без пробела («2026ООО») — из-за этого теряются контрагенты и заголовок, чинить в `blocks.py` нельзя без согласования с `pageBlocks()`; «Ближайшие сроки» на обзоре пока демо (можно брать `validUntil`); переключатели правил в настройках не влияют на проверку; дообучение модели на ПК пользователя (LoRA) — идея на после этапа 6.

## Как запускать и проверять

### Тесты
- Python (pytest в venv **нет**, не ставить без спроса) — простой раннер:
  ```bash
  cd document-intelligence/ai-service && PYTHONIOENCODING=utf-8 venv/Scripts/python.exe -c "
  import sys,traceback; sys.path.insert(0,'.'); sys.path.insert(0,'tests')
  f=0
  for m in ['test_cross','test_assistant','test_search','test_checks','test_editor_converter']:
      t=__import__(m)
      for n in [x for x in dir(t) if x.startswith('test_')]:
          try: getattr(t,n)()
          except Exception: f+=1; print('FAIL',m,n); traceback.print_exc()
  print('failures',f)"
  ```
- Java: `cd document-intelligence/java-backend && mvn -o -q test` (Maven офлайн, зависимости в ~/.m2).
- Синтаксис JS: `node --check <file>`.

### Сквозная проверка, не трогая запущенный Documentum
Рабочий Documentum занимает 8000/8085. Тестовые копии поднимаем рядом с **временной базой в scratchpad**:
- AI: `venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001` (в фоне)
- Java: `mvn -o -q spring-boot:run "-Dspring-boot.run.arguments=--server.port=8086 --ai.service.url=http://127.0.0.1:8001 --spring.datasource.url=jdbc:h2:file:<scratch>/db;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE --file.upload-dir=<scratch>/uploads"` (в фоне)
- UI: предпросмотр `ui-v2` из `.claude/launch.json` (порт 5173), открывать `http://localhost:5173/?api=http://127.0.0.1:8086`. Файлы через file:// в панели браузера открываются без скриптов — только через предпросмотр.
- После проверки: остановить фоновые задачи **и** добить java.exe на 8086 (Maven-процесс оставляет дочерний JVM), проверяя командную строку процесса перед остановкой.

### Обновление сборки у пользователя
Пока окно Documentum открыто, jar занят, а лаунчер каждые 5 с перезапускает упавшие службы — подменить на ходу нельзя. Порядок:
1. Пользователь закрывает Documentum (или штатно закрыть окно `Documentum-UI` через CloseMainWindow — лаунчер сам остановит службы). Проверить, что 8000/8085 свободны.
2. `cd document-intelligence/java-backend && mvn -o -q package -DskipTests`
3. `cd document-intelligence/electron-app && npm run build:portable`
4. Запустить `Documentum.exe` (Start-Process) и дождаться `/api/editor/documents` на 8085.
Python обновляется сам (запускается из исходников).

### Параметры запуска UI (для демо и снимков)
`?screen=editor|assistant|registry|search|settings|overview`, `&ask=<вопрос>` (можно несколько — уточнения подряд), `&still=1` (без анимаций), `&api=<адрес сервера>`.

## Грабли, на которые уже наступали
- **PowerShell не различает регистр имён переменных**: `$s` в цикле затирает `$S`. `$args` — служебная переменная. Давать уникальные имена (`$job`, `$scratch`).
- Python с `-I` игнорирует `PYTHONIOENCODING` — кириллица в консоли станет кракозябрами (данные при этом верные).
- curl с кириллицей в аргументах на Windows шлёт cp1251 → Java отвечает 400; JSON с кириллицей отправлять из Python.
- Не называть методы клиента API одинаково (`API.check` — проверка доступности сервера; проверка документа — `API.checkDoc`).
- При постановке пометки на текст внутри `<b>` граница диапазона должна попадать внутрь текстового узла (иначе остаётся пустой `<b></b>` и документ ложно «изменён»).
- Тестовая копия AI-сервиса (8001) пишет в тот же ai-service/data/search.db, что и рабочая: сверка с тестовой базой стирает рабочий индекс. Рабочий сервер сам восстановит его при следующем запуске, но после проверки тестовые записи из индекса надо убрать.
- Любой тестовый сервер данных, которому дали адрес рабочего AI-сервиса (`--ai.service.url=http://127.0.0.1:8000`), при старте сверяет индекс со своей пустой базой и **стирает рабочий индекс вместе с отпечатками**. Тестовой Java давать тестовый AI (8001) или несуществующий адрес; если всё же стёрли — перезапустить Documentum, индекс восстановится сам (на 5 документов — около минуты).
- Каталог, из которого запускали команду в консоли, остаётся занятым: папку `dist` нельзя удалить, пока в ней «стоит» оболочка. Скрипт сборки это терпит (пустые папки не мешают).
- Если интерфейс новый, а сервер старый, UI показывает «Сервер Documentum старой версии» — значит, нужна пересборка (см. выше).
